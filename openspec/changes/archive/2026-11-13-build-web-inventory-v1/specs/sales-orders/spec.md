# Spec Delta

## Purpose

以确认销售订单作为首次销售记账入口，允许管理员保留历史地更正订单，并使成交金额、批次成本、库存、优惠及客户应收整体一致，配送单打印保持独立。

## ADDED Requirements

### Requirement: 同一会话多商品选品与后续编辑
系统 MUST 支持管理员在电脑同一个选品弹窗、手机同一个全屏选品会话内选择多个商品；每条已选行分别配置仓库、销售单位、正整数数量、成交单价及自动或手动批次分配。搜索或切换当前商品 MUST 保留其他已选行的配置，统一确认后加入订单；取消会话 MUST 不改变原单。加入后 MUST 允许在订单页行内修改常用字段或展开该行必要配置，不得强制每改一行都重开选品弹窗。同商品不同仓库、单位或价格 MUST 保持独立行，不静默合并；选品和编辑不预留库存，金额与整单库存校验沿用既有后端报价及确认规则。

#### Scenario: 同一会话配置多个商品
- **WHEN** 管理员在同一选品会话配置商品甲，再搜索并配置商品乙，随后切回商品甲
- **THEN** 两条已选行及各自仓库、单位、数量、单价和批次方式均保留，统一确认时一起加入订单，不要求每个商品另开一次弹窗

#### Scenario: 同商品保留不同配置
- **WHEN** 管理员在会话中为同商品选择不同仓库、单位或成交价格的多条明细
- **THEN** 各行分别保存配置并参与全单库存联合校验，系统不按商品标识静默合并

#### Scenario: 加入后继续编辑
- **WHEN** 多条商品已加入订单，管理员需要修改其中一行数量、单价或仓库/批次配置
- **THEN** 可在订单页行内修改或展开对应配置，其他行保持原配置；无需为每次行编辑重新进入选品弹窗，正式提交仍遵循草稿、版本及确认规则

#### Scenario: 取消选品会话
- **WHEN** 管理员在会话中增加或修改了候选行后选择取消
- **THEN** 进入会话前的订单内容保持不变，不写入草稿、确认销售或产生库存预留

#### Scenario: 手机切换已选商品
- **WHEN** 管理员在同一个手机全屏会话中搜索多个商品并切换配置
- **THEN** 已选清单及每行配置持续保留，最终统一确认加入订单，取消仍不改变原单

### Requirement: 草稿与确认边界
系统 MUST 支持保存尚未记账的订单草稿，成功确认时才同时生效销售金额、库存扣减、批次成本、销售毛利和客户应收。任一明细缺货或校验失败时 MUST 整单不生效，不部分扣库。

#### Scenario: 保存草稿
- **WHEN** 管理员保存含客户和商品的草稿
- **THEN** 系统不预留库存，不确认销售、毛利或客户欠款

#### Scenario: 一行缺货
- **WHEN** 订单多行中仅一行在所选仓库不足
- **THEN** 所有行均不记账，返回具体缺货项，原库存不变

### Requirement: 整单优惠与抹零
系统 MUST 支持管理员成交单价、整单优惠及减免式抹零；按各行优惠前金额比例分摊并确定尾差，分摊合计等于整单减免。系统 MUST 按实际成交净额减实际成本计算毛利，允许负毛利但不允许负订单应付额。

#### Scenario: 比例分摊
- **WHEN** 两行金额分别为 60.00 和 40.00 元，整单减免 10.00 元
- **THEN** 两行分别分摊 6.00 和 4.00 元，订单实际金额为 90.00 元

#### Scenario: 优惠超过金额
- **WHEN** 总减免超过可减免商品金额
- **THEN** 系统拒绝确认或修改，不生成负应付货款

### Requirement: 保留版本的局部修改
系统 MUST 允许管理员修改已确认订单，不受已打印或已配送限制；保存前后版本，重算受影响金额和成本。未变更明细保持原分配，改价不动库存，改数量、商品、仓库或批次才调整相关库存；修改失败 MUST 保持原单与全部库存。

#### Scenario: 仅改售价
- **WHEN** 已配送订单仅修改成交价
- **THEN** 金额和毛利重算，原批次、销售成本和库存不变，并新增可追溯版本

#### Scenario: 增量缺货
- **WHEN** 修改订单增加数量但所选仓库不足
- **THEN** 整次修改失败，原版本和库存继续有效

#### Scenario: 未改行的成本
- **WHEN** 修改一行商品，同时另一行已有新进价批次
- **THEN** 另一行的历史批次成本保持不变

### Requirement: 更正不能重复处理退货
系统 MUST 保留已确认退货的数量、金额和批次来源；后续修改只作用于可修改部分，不得删除已退历史、降低至已退量以下或重复回补。必要时 MUST 把已退部分保留为只读历史段并拆分未退部分，以整数基础数量处理。

#### Scenario: 退货后减量
- **WHEN** 某明细已有退货，管理员尝试将有效销售数量改到累计已退数量以下
- **THEN** 系统拒绝并返回关联退货信息，不重复返库或抹除来源

### Requirement: 未配送订单作废
系统 MUST 支持管理员作废尚未配送的已确认订单，保留原单、恢复原仓原批及成本，撤销销售效力并调整客户应收；已发生的实收实退记录不能自动删除或冒充退款。

#### Scenario: 作废已收款未配送单
- **WHEN** 管理员作废已经收款但未配送的订单
- **THEN** 库存按原来源恢复，销售及应收撤销，实收记录保留并成为相应客户余额

#### Scenario: 已配送直接作废
- **WHEN** 管理员请求直接作废已配送订单
- **THEN** 系统拒绝作废，管理员仍可按修改或退货规则处理

#### Scenario: 作废已有部分返库的未配送单
- **WHEN** 未配送订单已有部分退货及实际返库，管理员作废整单
- **THEN** 系统保留原退货和返库事实，将商业退货调整并入作废，仅恢复尚未回补部分，关闭待返库任务且不重复扣销售或加库存

### Requirement: 幂等与并发修改
系统 MUST 对确认、修改、作废使用幂等请求标识及版本校验；相同请求重试返回原结果，相同标识不同内容报冲突；过期版本不得覆盖已提交新版本。

#### Scenario: 相同请求重复确认
- **WHEN** 同一确认请求在网络超时后重试
- **THEN** 返回同一业务结果，只产生一次销售、成本、库存和应收变化

#### Scenario: 两人修改同版本
- **WHEN** 两个管理员基于同一版本提交不同修改
- **THEN** 至多一项提交，另一项提示刷新，不静默覆盖
