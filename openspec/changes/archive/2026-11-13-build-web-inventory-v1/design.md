# Design

## Context

背景见 [proposal.md](proposal.md)。初始规划时仓库只有 AGENTS、术语、Wayfinder 记录和 OpenSpec 骨架，十项能力均为新增 delta specs；当前实现与验收进度见 [tasks.md](tasks.md)。2026-11-11 的调整只同步已授权的选品交互和视觉交接，主规格在变更实施及同步/归档前不改写。

约束：TypeScript 全栈、React 网页；Codex 只实现后端与契约，Antigravity 只实现前端；现有生图保留为业务草图，由 Gemini 重新视觉设计，用户已授权从草图重新设计并实现，最终视觉仍待验收。单商家、联网、手机和电脑基本功能一致，按角色授权。

## Goals / Non-Goals

**Goals:**

- 将销售、库存、成本、客户往来的一次业务操作作为一致性边界。
- 给出可直接拆分开发的表、约束、请求响应、权限、错误和验收依据。
- 保留单据及数据来源版本，使修改、退货、报表与打印能够核对。

**Non-Goals:**

- 本次文档调整生成应用代码、迁移、UI 或执行部署。
- 原生客户端、离线销售、自由拖拽打印编辑器、复杂调拨审批、完整会计总账。
- AI 执行任意 SQL、库存/订单/资金写入或自行转账。

## Decisions

### 1. 模块化单体与共享契约

建议后续目录为 `apps/api`、`apps/web`、`packages/contracts`、`packages/database`；API 内按身份、商品客户、库存、销售、往来、打印、报表、AI 分模块。采用 Fastify、Drizzle、PostgreSQL，接口以[契约说明](docs/api-contract.md)和[OpenAPI](docs/api-contract.openapi.json)为准，表结构见[数据库设计](docs/database-design.md)。

相比分布式服务，单库事务能覆盖订单跨仓批次扣减和客户往来，降低个人维护成本；相比把计算分散到前端，统一后端计算可使手机、电脑与 AI 一致。依赖具体版本在实施时查证并锁定，不假定已有工具脚本。

### 2. 明确状态、版本和业务时间

- 订单状态 `draft / confirmed / voided`；`version` 是并发写版本，`revisionNo` 是商业内容版本。首次确认时间固定，修改不改变原销售归属。配送仅用 `not_delivered / delivered` 元数据控制作废资格，不产生出库或毛利。
- 已确认改单生成不可变内容版本；草稿可更新但不占库存。打印日志追加不增加订单商业版本，也不令管理员改单因员工打印而冲突。
- 退货先确认信用额，返库、退款分别有独立记录。实际返库按原仓原批；未返库不进可售库存，待返库与明确损失分开。
- 每笔关键记录分别保存业务时间与登记时间。销售/改单按原确认时间归期；退货按确认时间；实收实退按实际时间；库存更正按实际生效流水，不能把后来批次消耗倒记到原订单日。

采用版本与追加事件，而不是覆盖一张订单后重算所有历史；无需建设完整事件溯源框架，当前快照用于查询，旧版和来源流水用于追溯。

### 3. 数量、货币和成本精度

- 数量及单位倍率为正整数；基础数量及合计不得超过 JavaScript 安全整数范围，数据库使用 bigint 并约束范围。首版不接受称重或小数输入。
- 金额 `numeric(20,2)`，成交单价及实际入库单位成本 `numeric(20,6)`；API 均传十进制字符串。中间换算使用至少 18 位小数或整数分子/分母，保留输入成本和倍率，不把基础单位成本提前舍入到分。
- 结算按分、四舍五入（half-up）。行金额先确定，再汇总订单；优惠及抹零按行金额比例以分分配，最大余数法、并列按稳定行顺序，使合计严格等于减免额。
- 批次同时保存原单位成本依据和剩余成本金额。分批成本分摊保留累计量、金额和尾差，最后出清承接余额；退回按原来源已分摊金额按量分配，累计不能超过原来源。所有成本分摊必须满足数量/金额守恒，不只依赖高精度近似除法。
- 实收实退不能由订单优惠差额替代。零价或负毛利允许；负数量、负单价、负应付或超额回退不允许。

这比全程两位单价避免拆零误差，也比仅使用高精度浮点却忽略尾差更容易对账。具体入参与字段上限在契约中固定，并使用分批销售、全部退回等性质测试验证守恒。

### 4. 库存与事务锁定边界

`inventory_batches` 是批次数量/成本依据，`stock_balances` 是同事务维护的商品仓库汇总与锁定锚点，不能成为另一份独立库存真相；支持由批次和流水核对重建。

写入顺序统一为：幂等记录 → 关联订单（有则锁定）→ 客户账户（按客户标识排序）→ 商品仓库汇总（按商品、仓库标识排序）→ 批次/消耗来源（稳定标识排序）。入库、盘点、销售、更正和返库都遵守该顺序，不能只在销售路径加锁。

自动分配按 `received_at, recorded_at, id` 选择正余量批次；手动模式保持明确选择，不足返回 `BATCH_SELECTION_REQUIRED`。同商品重复行先合并需求校验，再按行分配。确认以实时库存为准，报价只作预估，不建立库存预留。

库存、成本、单据新版本、商业应收、审计与幂等结果在一次事务提交。死锁或序列化冲突执行有限次相同幂等语义重试，仍失败返回可重试冲突；禁止一部分成功后向客户端要求补另一部分。

### 5. 订单局部修改、退货来源与作废

- 不变明细引用原消耗段；改价不动库存。增量新增消耗段，减量只释放尚未被退货占用的段，默认后扣先退。改商品、仓库或手动批次仅释放并重分配受影响部分。
- 退货记录原版本的净成交、成本与消耗来源。已退部分保留为只读历史段，后续价格或优惠只作用于未退部分；必要时拆为基础单位的整数段。派生历史段显示基础数量，不要求用户输入小数件数。
- 修改不得使有效总数量小于已退数量，不能删除退货来源。整单优惠不能低于已经锁定在已退部分的优惠额；返回明确冲突，允许管理员保留原部分并改单其余内容。
- 未配送作废恢复尚未通过改单或返库恢复的出库量。若已有退货，保留原退货及返库事实，将其商业调整标识为并入整单作废，关闭待返库任务并撤销相应有效退货信用额，防止销售、毛利和库存重复冲销；已发生现金记录不删除。退货关联的明确损失也通过来源冲正，不能默默变成新的盘盈。

API 的确认改单采用按行命令，不要求前端把整个历史订单复制覆盖。后端返回规范化的新版本与只读历史段，前端只按契约展示，不能自行重建成本。

#### 选品会话与订单页编辑

- 电脑用同一个选品弹窗选择多个商品，手机用同一个全屏选品会话；每条已选行分别设置商品、仓库、单位、正整数数量、成交单价及自动/手动批次。具体视觉布局由 Gemini 重做，不以旧图左右分栏或单商品配置页为约束。
- 已选清单与当前查看商品分开保存；改变搜索词或切换商品只切换展示，不清空其他行的配置。允许同商品按不同仓、单位、价格保留多行，不按商品 ID 静默合并。行以稳定的客户端行标识关联配置及报价。
- 会话内编辑是待应用的本地工作副本；统一确认后才加入订单页，取消不更改进入会话前的订单，也不逐行调用订单写入或确认接口。保存草稿和正式确认仍是独立明确动作。
- 加入后在订单页行内修改数量、单价等常用字段，仓库、单位和批次需要更多空间时展开该行配置；不强制每次编辑一行都重开选品弹窗。已确认订单沿用版本、原因及只读退货历史段规则。
- 2026-11-11 用户对新电脑外观反馈“确认按钮放到下面”：订单创建、已确认改单及草稿详情的主确认操作放在订单内容底部；电脑位于明细下方，可采用 sticky，手机底部须避开导航和安全区，长单滚动后仍可达且不遮挡内容。沿用原报价有效性、角色、幂等与确认 handler，不新增确认流程；Picker 原底部统一加入操作不变。这是位置方向调整，不代表 11.1 最终视觉已获接受。
- 选品、行编辑和预估报价均不预留或扣减库存。复用现有 `lines` 数组及 `POST /orders/quote`；对原订单加会话候选行的整体需求报价，正式金额、成本与库存校验均以后端为准。无需新增“批量选品写入”API；同仓重复商品行也必须参与联合校验。

该交互的前端验收归任务 12.3，文档更新不代表已实现或已完成验收。

### 6. 客户往来与更换客户

客户净往来 = 期初 + 当前有效订单金额 − 有效确认退货金额 − 实收 + 实退。正值是欠款，负值是客户余额；现金、订单应收和核销分别记录，抵扣只是核销已有资金，不再写一笔实收。

一笔收款可分配多单，一单可分次；默认按最早欠款，管理员可指定分配。核销总和不得超过同客户可用款与应收。金额降低后释放多余核销形成余额；现金纠错用冲正关联，不把错误登记更正伪装为实际退款。

订单更换客户时，逐笔重分类该订单商业应收及关联退货信用额，保持各自业务日期；实际收退款仍属于原客户，解除不再合法的核销并返原客户余额。不能只把净额统一移到原订单日，否则跨期退货会令月结不平。响应提供两个账户的变动摘要，用户明确操作后才提交。

### 7. 数据字典与服务端字段授权

管理员订单 DTO 与员工订单 DTO 分开定义。员工只取得配送、商品、成交和打印数据，不能靠返回 `null` 或前端隐藏保护成本。订单历史、错误详情、打印数据与来源跳转都使用相同投影；写接口先鉴权再读取幂等缓存，防止降级后重试拿到管理员旧响应。

采用同源 Cookie 会话、来源检查及 CSRF 挑战；登录前匿名会话仅取得挑战，不能访问业务，登录后轮换会话与令牌。共享契约的响应校验必须按角色选择 schema，不把通用 union 验证当成字段授权证据。

商品助记码保存自动生成值和可选人工校正值；改名重生、缺少新校正则清除旧覆盖，数字英文保序、小写、去空白标点。商品编码/条码唯一，助记码不唯一；已引用单位倍率和基础单位不可原地改义。

### 8. 打印配置与双端交付

现有 `docs/ui/build-web-inventory-v1/v3/` 图片未获用户接受，只向 Gemini 说明页面职责、业务信息与数据示例；不要求沿用其配色、字体、圆角、密度或像素布局。保留原稿和用户参考，由 Gemini 重新设计；本次不继续生图、不要求先补齐全部新图；用户本次已授权从草图重新设计并实现，最终视觉仍待验收。操作交接见 [gemini-handoff.md](../../../docs/ui/build-web-inventory-v1/gemini-handoff.md)。主代理已使用实际可用的Computer Use将任务投递至Antigravity，模型Gemini3.8FlashHigh，会话`9d1031ba-b2f4-4f4d-9093-880204382c88`当前Working；本轮Codex只同步文档，前端效果待实际验收。

模板配置是有版本的 JSON，纸型、字段、毫米列宽和最小行高经后端白名单校验；真实排版、预览和浏览器调用由 Antigravity 前端实现。默认一张客户配送单保留全单多仓明细，仓库字段可显示；打印数据固定订单内容版本及模板版本，不包含成本毛利。

发起打印写 `requested`，人工回执可为 `user_confirmed / user_cancelled / client_error`；浏览器事件不生成实际出纸保证。订单商业版本变化后旧日志不算新版已发起。模板改版不抹掉旧记录，补打可选明确模板版本。

### 9. 统计快照与 AI

统一指标服务为固定报表与 AI 提供规范化查询。订单按原确认期间的有效版本；退货按确认期间；现金按实际发生期间。下单量与退货/净销量分列，客户商品比较取两期组合并集并补零，基期为零不算百分比。

每次报表生成结果标识、截止点和来源版本清单，分页和明细沿用同一结果。报表在一致数据视图中计算，后续数据变化不混进旧页或旧明细；历史对账与报告可识别版本差异。库存默认当前账面，历史按流水追溯，入库业务日与登记日可分别筛选。

AI 适配器只生成受控查询意图，不拿数据库凭据；后端校验参数、权限、范围和时间限制，再调用相同指标服务。模型只解释证据，结构化数字始终来自后端，解释不合证据则用确定性摘要替代。密钥只在服务端配置，模型超时不持有业务事务锁。

## Risks / Trade-offs

- [历史月报会随改单变化] → 保留生成时点、来源版本及月结快照，显示重生成差异，不冻结管理员已明确允许的历史改单。
- [大量分批/折扣/退货出现尾差] → 以来源金额和剩余量约束分摊，末次承接余数，加入金额与数量守恒测试。
- [收款后换客户造成错账] → 商业应收重分类与现金账户分开，解除失效核销并返回变动摘要。
- [实际设备与网页排版有差异] → 在真实电脑与安卓手机验证页面和基本预览，并在支持打印入口的真实设备验证系统打印服务及实际预览；本轮不以物理打印机或实纸输出为验收前置，不把浏览器回调当出纸成功。
- [中文多音字及助记码碰撞] → 可人工校正、助记码非唯一、改名同步更新；实现时核查拼音库，不能只写覆盖例子的替换表。
- [AI 解释或参数出错] → 结构化校验、受控只读工具、精确表格与来源、超限和异常降级。
- [容量证据与实际负载存在边界] → 规模已明确为100–200商品、约100客户、日50单，复用已有隔离查询计划及并发实测；首发采用空业务初始化，不依赖真实期初资料，不将模拟历史或热缓存结果承诺为生产写入SLA。

## Migration Plan

1. apply 阶段建立工作区和契约，再按数据库设计生成可重复执行的初始迁移及测试数据库；本轮不创建迁移文件。
2. 先迁移全新空业务数据库，安全初始化首个管理员并完成必要基础配置，再启用业务；不自动注入演示客户、商品、库存、订单、期初批次或期初往来，初始库存、订单与往来为零。保留已有期初入库和期初往来能力及核对口径，期初欠款仍不能再算成新销售；本轮不要求真实期初资料或导入预检，导入导出留后续独立需求，不新增初始化向导。
3. 开发与生产采用相同 PostgreSQL 语义；部署前校验迁移、HTTPS、会话和字段权限，备份后升级，验证可恢复。
4. 首次空库迁移失败可回滚空库；已有真实数据后的失败优先向前修复或从备份恢复到隔离实例，禁止盲目回滚删除流水。上线回退使用兼容应用版本与经过验证的数据库恢复步骤。

## Open Questions

剩余验收包括已连接真实安卓手机的页面与基本预览、真实设备上的系统打印服务调用与实际预览，以及新空业务库安全初始化；手机已连接并开启USB调试不等于已通过实际验收。物理打印机、实纸输出与真实期初资料不是本轮前置，导入导出不纳入本轮实现。规模已明确；部署域名及模型服务配置仍按已有证据边界说明，不假定已取得。上述调整不改变已有业务口径与职责拆分。
