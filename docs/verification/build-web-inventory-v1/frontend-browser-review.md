## 历史P1：选择已保存地址后同时发送addressId与deliverySnapshot（当前GUI阻断已关闭）

已读源码定位：

- `apps/web/src/pages/sales/components/CustomerPickerModal.tsx:65`起handleConfirm：找到已保存addr时还构造一份用于展示的snapshot，随后同时回调`address:addr`和`deliverySnapshot:snapshot`（85–89行）。这种本地展示数据可以同时存在，问题发生在请求序列化。
- `apps/web/src/pages/sales/OrderCreatePage.tsx:560`附近回调同时保存selectedAddress与deliverySnapshot。
- 同文件`122–123`报价、`217–218`保存草稿、`271–272`确认前创建草稿，三处payload都无条件包含`addressId:selectedAddress?.id`及`deliverySnapshot`。因此本次选择DEMO-C1默认地址会同时传入二者；这不是其它未完成页面缺功能的推断。
- `apps/api/src/modules/catalog/service.ts:165`：`addressId && supplied`明确返回`INVALID_REQUEST`/400、“地址和配送快照不能同时指定”。浏览器已观察同文案；此处400/code来自源码对应，并非本轮声称已抓取Network日志。

### 契约与业务依据

当前OpenAPI在OrderDraftInput/OrderDraftPatch中分别列出可选addressId与deliverySnapshot，OrderQuoteInput复用OrderDraftInput；这不意味着二者可以作为两个并行地址来源。业务服务明确要求选择其一：

- 已有启用地址：按所选客户所属addressId读取并由服务端生成/冻结AddressSnapshot。
- 显式本单快照：传完整AddressSnapshot（customerName/contactName/phone/address），不带addressId。
- 二者都省略时，后端仅按该客户有效默认地址处理；没有有效地址返回需要选择地址或填写快照，不能拿伪造空值绕过。

### 交Gemini的精确修复要求

1. 报价、保存草稿、确认前创建草稿三处使用同一地址来源选择规则，不能只补quote而留下实际写入仍冲突。
2. 选中已有地址时请求只发送addressId；UI可保留独立展示用snapshot，但不无条件把它序列化进请求。服务端负责由地址资料形成订单快照。
3. 仅在用户明确使用本单快照来源时发送deliverySnapshot，排除addressId；切回已有地址后不得把上一份快照夹带到wire。不要为绕过报错新增未授权业务或猜测后端字段。
4. 客户/地址来源改变后让旧报价失效，再获取与当前请求内容一致的新报价；只有当前有效quote才可确认。已修的并发代次、幂等键与版本保护保持。
5. 不修改后端业务校验，不让后端放宽双地址来源；共享contracts与根配置也不因该前端序列化错误改动。
