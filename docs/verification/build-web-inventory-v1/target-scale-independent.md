## 并发与计划证据

- 5并发读取是Promise.all五个worker，每个读不同客户ledger首50与balance；5确认是Promise.all五个真实事务，共享客户99、同仓同3商品，真实进入账户/库存锁路径。结果分别整批18.722ms、59.842ms；确认前后库存总量恰少15。不是5浏览器登录用户，也不是日50单=并发50的压力承诺。
- 每个测量组先捕获真实PoolClient.query中的SELECT/WITH及原参数，按SQL文本组内去重，执行EXPLAIN ANALYZE BUFFERS FORMAT JSON。逐份结构核查均有Actual Rows、Actual Loops与Execution Time，非人工拼估计计划；10组数量分别1/6/9/1/2/1/4/4/3/3，合计**34份**，与results.uniqueSelectPlans逐组完全相同。
- 34指测量组内去重后的计划文件条目，**全文件不同SQL文本为25种**，不是全局34种不同SQL。候选订单逐单查询实际会执行多次，plan只保留相同文本的一组参数；不能用计划份数当完整SQL执行次数。
- 计划/单组服务测量在5并发确认之前，所以库存主计划扫描56,350流水，最终计数56,365包含后加15条；这是脚本顺序产生的正常差异。EXPLAIN本身亦是测量后的再次执行，不是3次调用之一。
- 10项服务耗时与报告四舍五入吻合：商品检索1.061–3.038ms、订单页14.960–22.608、50候选未结30.555–32.389、批次0.125–1.426、ledger0.463–3.322、历史价22.555–24.038、月结1.649–11.076、30日销售57.976–105.668、100客户余额212.697–227.627、库存96.969–156.787。是Node服务操作总耗时，不是HTTP/浏览器耗时；仅3次，不能推P95/P99。
- 历史价SQL25.809ms、库存主SQL58.930ms与报告一致；SQL单独EXPLAIN比某轮服务更慢并非矛盾，因为是另一次运行。库存temp written最大954块、read952块，且有Seq Scan；按当前整体97–157ms和该规模扫描，尚无证据要求盲目加索引/调大work_mem。shared hit是累计访问而非物理独立读页数，报告已准确说明。

## 执行环境与可支持边界

1. JSON硬件是Apple M5、10逻辑CPU、17,179,869,184 bytes=16GiB，PG18.6 Homebrew darwin/arm64，**不是Mac mini或Linux生产主机**。现有参数shared_buffers=16,384×8KiB=128MiB、work_mem=4096KiB=4MiB、max_connections=100；fixture业务pool最大8。报告数值一致，没有据此修改生产参数。
2. 生成后ANALYZE，数据/OS/PG缓存已热，报告明确非冷盘读。test-postgres私有cluster用`-F`关闭fsync，写入310.20s、五确认59.84ms不能当真实持久化提交SLA；总313.47s和JSON精度一致。
3. Node mock Date逐日推进业务确认/现金日期；PG默认登记时间仍为本轮真实时间。这是模拟历史事实密度，不是跑了一年真实持续负载，也不是全年按真实登记日分布。近30日明确custom范围2026-10-12T01:00Z至2026-11-11T01:00Z，不能称上海完整自然月。
4. 数据付款分布偏置为部分客户常结清、其余常未结；无本次退货/改单、真实期初、多年分布、持久化/磁盘故障、长时负载、网络或移动渲染/针式打印结果。作者最终报告逐项保留这些边界，未将其偷偷当0或已验。
5. 清理路径finally重置mock、db.cleanup物理连接关闭后删随机库，运行器停止私有PG并删临时目录；作者报告记录实际cleanup日志与exit0。独立复核没有重新执行该命令或亲自复现清理，不能把源码/产物核对表述成本代理再跑一次。
