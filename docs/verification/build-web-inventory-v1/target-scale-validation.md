# 用户目标规模后端容量验证

2026-11-11实际执行。结论：在本轮独立、热缓存、非持久化测试条件下，200商品/100客户/一年日50单样本的关键服务读查询、月结/报表与5并发探针完成，没有发现需要立即改表结构或生产参数的阻挡。此结论限定当前Mac硬件和下述数据分布，不等于生产SLA；期初资料待定，14.4仍不能整项完成。

## 用户信息与测试假设

协调者转述用户信息：“商品100–200、客户约100、日订单50、期初待定”；设备为安卓手机、连接电脑的针式打印机，已明确单份纸241×93mm。打印机型号和真实走纸/边距未实机验证，设备信息只是保留上下文，不是本容量测试结论。

测试取商品上限200、客户100，假设全年365日每天50单，共18,250历史订单；这不是50并发。其他明确测试假设：2仓、每商品每仓4个进货来源批次、每单3行、每行1–3瓶、进价2元/售价5元、每第五单实收并人工核销全额。没有声称这些仓数/行数/付款比例来自用户。付款分布为部分客户常结清、其他客户常未结，并非真实付款行为抽样。

历史业务范围2025-11-11起365日，模拟业务Date生成确认/实收时间，PG登记时间仍为本轮真实生成时刻。因此可用于历史销售期间/ledger/月结与当前库存读验证，不证明一年前已知视图或全年真实登记分布。没有期初导入、退货/改单占比和真实批次数分布资料，不伪造用户期初；本轮入库kind=opening仅是明确虚构库存夹具。

当前执行机Apple M5、10逻辑CPU、16GiB内存、darwin/arm64，PostgreSQL18.6 Homebrew；不是Mac mini或Linux生产机器。共享dev API、DEMO-C1和Mini都没有被修改、重启或同步。

## 计划观察与并发

- 商品检索SQL0.643ms，客户ledger主查询0.137ms，客户订单候选查询约1.527ms；服务层订单页约15–23ms体现了详情组装的额外SQL，不能把候选SQL耗时冒充整个页面。
- 同商品历史价SQL25.809ms、shared hit104,527、shared read0。存在重复页访问/关联读放大，当前绝对时间可接受，应在更长历史/真实改单与退货分布后再评估；shared hit是累计访问，不等于同样数量的独立物理磁盘页。
- 全仓库存主SQL58.930ms，顺序读56,350条库存流水，shared hit1,618/read0，temp written954块（按8KiB约7.45MiB），说明本次聚合/排序存在临时文件。第二来源查询15.954ms。当前总体服务约97–157ms，不能仅见Seq Scan或临时文件就盲目加索引/全局work_mem。
- 30天销售事实SQL17.774ms，部分顺序扫描customers100、products200、units200及相关revisions是正常可选计划；余额主SQL24.459ms，完整余额服务约213–228ms还包含来源集合、快照序列化与存储。
- 5并发读取（各ledger首50+balance）整批18.72ms；5个同客户/共享商品仓的真实确认整批59.84ms，5单均成功，库存数量恰减15；之后全库数量/成本/往来汇总仍守恒。未把这次5并发结果扩成50并发承诺，写耗时受-F边界限制。
